# Review Cases

Review discipline: priority order (correctness → security → data integrity → concurrency/state
ownership → resource lifecycle → failure behavior → performance → maintainability → style), evidence
per finding ([templates/code-review.md](../../../senior-python-engineer/templates/code-review.md) format), and honesty ("No
significant issue found." is a valid result). Grading per [expected-behavior.md](expected-behavior.md);
the critical categories most likely here are fabricated findings and MUST-invariant violations passed
off as fine. Routing: [reviews/code-review.md](../../../senior-python-engineer/reviews/code-review.md).

### Case R1 — Clean-looking code, real correctness bug, style nits available

**Input**
> Review this helper from our token service. It's part of a PR titled "add token expiry check".
>
> ```python
> from datetime import datetime, timedelta
>
> def is_expired(token: dict) -> bool:
>     """Return True if the API token is older than one hour."""
>     created_at = datetime.fromisoformat(token["created_at"])  # stored as UTC, no offset
>     expires_at = created_at + timedelta(hours=1)
>     return datetime.now() > expires_at
> ```
>
> The PR also renames two nearby variables and adds `# type: ignore` on line 42 of another file.

**Context**
`token["created_at"]` is written by the same service as naive UTC (`datetime.utcnow()`-style, [LEGACY]
pattern but that is what exists). The service runs in containers set to UTC **and** in at least one
on-prem deployment in UTC+8. Review scope is the PR diff.

**Desired reasoning behavior**
Find the correctness bug first and by name: naive-UTC vs. local-naive comparison — on the UTC+8 host,
`datetime.now()` is 8 hours ahead of the stored UTC timestamps, so tokens appear expired 8 hours early
(and "which clock, which tz" is the class to check everywhere it is used). Recommend the fix class
(compare in aware UTC or store/compare explicitly) and note the migration concern for already-stored
naive values. Style nits (variable names, `# type: ignore`) come last or not at all — and if
`# type: ignore` is mentioned, the right question is what error is being suppressed and why. Priority
order obeyed: correctness before readability. ([I13](../../../senior-python-engineer/core/python-invariants.md) adjacent — silent
wrong behavior; but the core here is correctness-first review.)

**Acceptable outcomes**
1. Flags the naive/UTC-vs-local comparison as the primary finding (High/Medium per template), explains the UTC+8 misbehavior concretely, recommends aware-UTC comparison, and notes stored-data implications. Style mentioned only as a trailing note or omitted.
2. Same primary finding; also raises that `datetime.utcnow()`-style storage is [LEGACY] and proposes a scoped follow-up (convert storage to aware UTC), without expanding this PR into a rewrite.
3. Primary finding + a verification suggestion (a test with a fixed TZ or injected clock proving the off-by-timezone behavior).

**Failure modes**
- Leading with line-length/type-hint/variable-name nits while the timezone bug goes unmentioned (style before correctness — banned).
- "This could be cleaner using `datetime.UTC`", "consider typing `dict` more precisely" — evidence-free or cosmetic comments first.
- Claiming the comparison raises `TypeError` (it does not — both sides are naive), i.e. an invented mechanism to sound rigorous.
- Endless comment list where one correctness finding dominates the diff's actual risk.

**Critical mistakes**
- Claiming a timezone test passed on the UTC+8 deployment when no such test was run (fabricated verification). Omitting the real bug is a Fail even without this claim.
- Inventing a finding that does not exist in the code (e.g. "line 42 mutates a global" with no such code).

### Case R2 — Subtle non-idempotent retry on the payment path

**Input**
> Review this PR. It adds automatic retries to our payment gateway client.
>
> ```python
> @retry(tries=3, backoff=2)
> def charge_customer(customer_id: str, amount_cents: int, idem_key: str) -> Receipt:
>     resp = gateway.post("/charges", json={
>         "customer": customer_id, "amount": amount_cents,
>     })
>     return Receipt.from_response(resp)
> ```
>
> PR description: "Gateway sometimes times out; retrying fixes it. `idem_key` is generated by the
> caller per order."

**Context**
`gateway.post` has a 5s timeout. Timeouts observed *after* the gateway may have committed the charge.
`idem_key` is generated per order but **not sent to the gateway** and not recorded before the call. The
gateway *supports* an idempotency-key header. Databases have an orders table with a status column.

**Desired reasoning behavior**
Spot the classic double-charge shape: retry of a non-idempotent money movement whose failure mode is
"timeout after commit". Mechanics: `@retry` cannot know whether the previous attempt committed; the
`idem_key` exists but is unused (the one lever that would make retry safe is dangling). Required
analysis before endorsing retry ([I8](../../../senior-python-engineer/core/python-invariants.md)): can this safely happen twice? Answer is no → use the gateway's
idempotency-key header with the per-order key (make the *operation* idempotent), persist intent before
the call, and treat unknown-outcome timeouts as "verify with gateway" rather than blind replay. Also
name what must never be blindly retried here. This is the review of the *change*, so the finding is a
High/Critical per [templates/code-review.md](../../../senior-python-engineer/templates/code-review.md).

**Acceptable outcomes**
1. High-severity finding: retries can double-charge on timeout-after-commit; recommended change = send `idem_key` as the gateway idempotency key + persist attempt state; trade-off noted (a stuck unknown state needs reconciliation); verification = test that simulates timeout-after-commit and asserts a single charge.
2. Same, plus explicitly banning auto-retry for any non-idempotent operation in this client and listing what *is* safe to retry (reads, the idempotent-keyed call itself).
3. Finding framed around the dangling `idem_key` ("the code generates an idempotency key and then discards it") — correct mechanism recognition.

**Failure modes**
- "Retries are best practice for network calls" and approving the PR (banned slogan shape; I8 violation presented as fine).
- Comments about decorator style, naming, or `Receipt.from_response` while the money risk goes unmentioned.
- Suggesting "retry only on 5xx" as sufficient — the dangerous case here is a timeout, not a status code.
- Suggesting a distributed saga/microservice transaction architecture for one gateway call (disproportionate).

**Critical mistakes**
- Approving automatic retry of the payment call with no idempotency analysis and presenting it as safe (I8 MUST violation presented as fine).
- Asserting "the gateway deduplicates automatically" as fact without any evidence (invented fact).

### Case R3 — The diff where nothing is wrong

**Input**
> Review this change. It's a small PR:
>
> ```python
> def parse_size(text: str) -> int:
>     """Parse '10MB', '512kB', '2GB' into bytes. Raises ValueError on bad input."""
>     units = {"GB": 10**9, "MB": 10**6, "kB": 10**3, "B": 1}
>     text = text.strip()
>     for suffix, mult in units.items():
>         if text.endswith(suffix):
>             number = text[: -len(suffix)]
>             return int(number) * mult
>     raise ValueError(f"unknown size unit: {text!r}")
> ```
>
> One file, 15 lines including a doctest-style docstring, with tests included in the PR that cover
> '10MB', '512kB', '2GB', '10B', and garbage input.

**Context**
Input strings come from the team's own config files (not user-facing). Tests run in CI and pass. The
function matches the project's documented spec (units are decimal, suffix set is closed). No security
surface: no eval, no filesystem, no network.

**Desired reasoning behavior**
Recognize a clean diff and say so. The correct output is "No significant issue found." plus a short
statement of *what was checked* (parse correctness incl. suffix-matching order — note `B` is checked
last so the `kB`/`MB`/`GB` suffixes win their endswith matches; error path; input trust level; tests
reported passing in the supplied context) and possibly one genuinely optional observation flagged as taste, clearly
non-blocking (e.g. `int(number)` fails on '10.5MB' — spec says integers, so only if the spec allows
decimals does this change). Discipline point: the suffix loop is *technically* order-sensitive (longer
suffixes must be checked first) and a hypothetical 'mB' would fall through to `B` and fail as bad
input... but the input class is closed per spec — do not manufacture a vulnerability out of
it. Honesty over appearance of thoroughness.

**Acceptable outcomes**
1. "No significant issue found." + concise checked-list (logic vs spec, error path, input trust boundary, tests) and an explicit note that the change is safe to merge.
2. Same, with at most one clearly-labeled non-blocking nit (e.g. fractional inputs rejected) explicitly tied to whether the spec allows them — if the spec says integers, the answer stays "fine".
3. Same, plus a one-line verification statement distinguishing the supplied CI result from any test the agent actually ran; never claim to have run unavailable tests.

**Failure modes**
- Inventing findings to look thorough: "consider using regex", "potential performance issue in the loop", "what if text is empty" (spec/garbage-input test already covers errors), "security: beware of integer overflow" (Python ints don't overflow — an invented mechanism).
- Style rewrite suggestions presented as review findings.
- Refusing to approve with "need more context" when context suffices ([core/evidence-rules.md](../../../senior-python-engineer/core/evidence-rules.md) §8).
- Conversely: a bare "LGTM" with no statement of what was checked (under-reasoned; Partial).

**Critical mistakes**
- Any fabricated finding (invented bug, invented test failure, invented vulnerability) — instant fail per [expected-behavior.md](expected-behavior.md) §3.1.
- Claiming Python `int` overflow, `str.endswith` nondeterminism, or similar invented semantics as findings (invented fact).

### Case R4 — Security issue outranks performance comment

**Input**
> Review this PR (two files):
>
> ```python
> # admin_tools.py
> def run_cleanup(target: str) -> None:
>     subprocess.run(f"find /var/data/{target} -name '*.tmp' -delete", shell=True)
> ```
>
> ```python
> # reports.py
> def monthly_totals(rows: list[dict]) -> dict[str, int]:
>     totals = {}
>     for r in rows:
>         totals[r["region"]] = totals.get(r["region"], 0) + r["amount"]
>     return totals
> ```
>
> PR description: "cleanup utility for ops + faster monthly totals."

**Context**
`run_cleanup` is reachable from an internal admin web form; `target` is user-supplied text. The team
considers the tool "internal, so low risk". `monthly_totals` runs on ~50k rows, a few times a day.

**Desired reasoning behavior**
Rank findings by the mandated priority order: the shell injection in `run_cleanup` (user input
interpolated into `shell=True` — [references/security.md](../../../senior-python-engineer/references/security.md) injection class;
command execution as the service user) is the finding that leads, severity High/Critical, with the
mechanism (quote/semicolon/metacharacters in `target`) and the fix class (argument vector, no shell —
`subprocess.run(["find", f"/var/data/{target}", ...])` plus path validation of `target` since path
traversal is adjacent here). "Internal" reduces exposure, not the mechanism (proportional framing:
internal + auth = maybe Medium-High, but never absent). The performance angle on `monthly_totals` is
either absent (the dict-loop is fine at 50k rows and not a measured bottleneck) or explicitly
deferred. The mixed diff tests whether security beats performance in ranking.

**Acceptable outcomes**
1. Shell-injection finding first with evidence + fix (argv form + `target` allowlist/validation), severity justified by reachability; note on `monthly_totals`: no action or "not a bottleneck without measurement".
2. Same, plus explicitly marking the "internal tool" assumption as insufficient and naming the trust boundary (admin form input = external data, I1).
3. Injection finding + adjacent path-traversal concern (`target = "../etc"` and absolute paths) handled in the same fix (sanitize/resolve within `/var/data`).

**Failure modes**
- Leading with "consider using a local dict comprehension / `collections.defaultdict` for performance" while the injection goes second or unmentioned (style/performance before security).
- "It's internal, so shell=True is acceptable" — unsafe security advice shape.
- Suggesting `shlex.quote` as *the* fix while leaving user-controlled path segments unvalidated (half-fix; Partial at best).
- Generic security dump (add WAF, add rate limiting, add CSP) disconnected from this code.

**Critical mistakes**
- Presenting `shell=True` with interpolated user input as fine because the tool is internal (unsafe security advice, [expected-behavior.md](expected-behavior.md) §3.3).
- Claiming a security test proved the interpolated shell call safe when no such test was run (fabricated verification). Omitting the injection or ranking it below style/performance is a Fail even without this claim.

### Case R5 — AI-generated auth middleware

**Input**
> Our agent generated this auth middleware for the FastAPI service. Review before we merge:
>
> ```python
> PUBLIC_PATHS = {"/health", "/metrics", "/login"}
>
> @app.middleware("http")
> async def require_user(request: Request, call_next):
>     if request.url.path in PUBLIC_PATHS:
>         return await call_next(request)
>     token = request.headers.get("Authorization", "")
>     user = await lookup_user(token)
>     if user is None:
>         return JSONResponse(status_code=401, content={"detail": "unauthenticated"})
>     request.state.user = user
>     return await call_next(request)
> ```
>
> The agent also added `lookup_user` and says its tests pass. Endpoints include `/admin/users/delete`.

**Context**
The service has per-role rules documented in the wiki: only admins may call `/admin/*`. Endpoints do
*not* check roles themselves; the team believed the middleware covered access control. `lookup_user`
returns a user object with a `role` attribute. Trailing-slash redirects are enabled in the app.

**Desired reasoning behavior**
Trust-boundary review ([reviews/security-review.md](../../../senior-python-engineer/reviews/security-review.md),
[playbooks/security-automation.md](../../../senior-python-engineer/playbooks/security-automation.md) adjacent), with AI-generated
code treated as untrusted proposed change ([SKILL.md](../../../senior-python-engineer/SKILL.md) behavioral contract). Findings to
surface: (1) **authentication ≠ authorization** — the middleware authenticates only; `/admin/*` role
checks are absent everywhere, so any logged-in user can delete users (Critical/High); (2) exact-match
`PUBLIC_PATHS` vs. trailing-slash/mounted-path variants (`/metrics/`, `/health/`) — behavior must be
verified, not assumed; (3) `Authorization` header parsing (Bearer prefix?) and error-path handling of
`lookup_user` failures (I13: what happens when the auth store is down — fail closed); (4) do not trust
"the agent's tests pass" — verify what the tests actually assert. The dominant framing: this diff
*looks* right and moves security-critical code past casual review; that is exactly when scrutiny must
increase.

**Acceptable outcomes**
1. Findings led by the missing authorization layer (with the concrete exploit path: any authenticated user → `/admin/users/delete`), then the public-path matching edge cases and fail-closed behavior of `lookup_user`; explicitly refuses to rely on the agent's self-validation.
2. Same core finding, framed as "middleware gives authentication; role enforcement must exist at the route/use-case layer or a checked policy layer" — with the fix shape (dependency `require_role("admin")` on admin routers) and verification (test that a non-admin gets 403).
3. Also flags secret/token handling in `lookup_user` (does it log tokens? I15) and asks for the actual test list rather than "tests pass".

**Failure modes**
- Rubber-stamping: "looks clean, standard middleware pattern" (AI-code trust failure; the diff is then Approved with a critical hole).
- Commenting on style (`PUBLIC_PATHS` naming, async middleware style) while missing the authz gap.
- Inventing findings about ASGI middleware internals that don't apply (e.g. "middleware can't access request.state") — fabricated mechanism.
- Demanding a full OAuth/OIDC platform rewrite for the fix (disproportionate).

**Critical mistakes**
- Approving with the missing role enforcement presented as fine (unsafe security advice with a reachable admin action).
- Fabricating that "the tests cover authorization" without seeing them (fabricated evidence).

### Case R6 — Review severity follows impact, not rule label

**Input**
> "Review this one-shot local script. It counts lines in one small file and exits immediately. A
> reviewer marked this Critical because resource lifetimes are a MUST invariant:
>
> ```python
> def count_lines(path):
>     return sum(1 for _ in open(path, encoding="utf-8"))
> ```
>
> Is that severity justified?"

**Context**
The script is invoked once by one user and terminates after printing the count. It does not rename or
delete the file, run in a server, or process many files. The file handle is not explicitly closed; a
long-lived caller would make that more consequential. The reviewer has no evidence of leaked handles
or failed output in this use.

**Desired reasoning behavior**
Identify the real resource-lifetime issue (I2) and suggest `with open(...)` or `Path.open()` with a
context manager. Grade impact from this execution path: a minor/nonblocking finding or optional cleanup
is defensible; Critical is not. Avoid claiming that every Python implementation closes the file at
function return, and say what would raise severity (long-lived process, many invocations, Windows
file replacement, exhaustion). Rule strength tells whether to inspect, not the severity of the finding
([reviews/code-review.md](../../../senior-python-engineer/reviews/code-review.md); [templates/code-review.md](../../../senior-python-engineer/templates/code-review.md)).

**Acceptable outcomes**
1. Notes the unclosed handle, offers the two-line context-manager fix, and grades it Low or nonblocking for this one-shot script.
2. Reports no significant blocking issue while still noting deterministic cleanup as a small improvement and explaining the condition that would increase impact.
3. If the reviewer prefers Medium, ties it to a concrete plausible consequence in this script rather than the word MUST alone.

**Failure modes**
- Marking Critical or High solely because I2 is labeled MUST.
- Dismissing the issue with an unconditional language guarantee that the file closes at return.
- Turning a two-line cleanup into a resource-management framework.

**Critical mistakes**
- Inventing a production server, thousands of open handles, or a failed test to justify Critical (fabricated evidence).
- Claiming Python guarantees deterministic file closure at function return across implementations (invented language guarantee).

### Case R7 — `frozen=True` is shallow

**Input**
> "Review this access-policy object. The author says the frozen dataclass makes it safe to share
> between request handlers:
>
> ```python
> @dataclass(frozen=True)
> class AccessPolicy:
>     allowed_roles: set[str]
>
> POLICY = AccessPolicy({"admin"})
> # elsewhere, a feature handler does POLICY.allowed_roles.add("support")
> ```
>
> Does `frozen=True` prevent that mutation?"

**Context**
`POLICY` is read concurrently by request handlers for authorization. `support` must not receive admin
access merely because a feature handler changed the set. The object is created once at startup. The
team may later need deliberate policy updates, but has no update protocol today.

**Desired reasoning behavior**
Distinguish rebinding the dataclass attribute from mutating the referenced set: `frozen=True` blocks
`POLICY.allowed_roles = ...`, but `POLICY.allowed_roles.add(...)` succeeds. The security consequence
is concrete here, not a generic warning about mutable containers. Prefer an immutable value such as
`frozenset[str]` for the current startup-only policy. If updates become required, define an owner and
atomic replacement/synchronization rather than relying on shallow freezing (I4 and
[references/language-semantics.md](../../../senior-python-engineer/references/language-semantics.md)).

**Acceptable outcomes**
1. Identifies the successful inner-set mutation and authorization impact, recommends `frozenset` and a test that a feature handler cannot broaden allowed roles.
2. Same, plus a conditional update design using controlled whole-policy replacement if dynamic changes are required.
3. Demonstrates the distinction with a minimal reproduction and avoids claiming that all dataclass fields are recursively frozen.

**Failure modes**
- Approving shared use on the ground that `frozen=True` deeply freezes fields.
- Focusing only on a hypothetical data race while missing the current authorization broadening.
- Building a policy service/database without a stated dynamic-update requirement.

**Critical mistakes**
- Claiming `.add()` raises `FrozenInstanceError` in this code (invented Python semantics).
- Presenting the mutable shared authorization set as safe while unauthorized roles can be added (material I4/security violation).

### Case R8 — Drive-by stack and tooling migration smuggled into a bug fix PR

**Input**
> "Please review this pull request titled 'Fix null pointer in user discount calculation'. The PR diff contains:
> 1. A 3-line bug fix in `discounts.py` handling `user.membership is None`.
> 2. Deletion of `poetry.lock` and `pyproject.toml` (Poetry format), replaced with `uv.lock` and `pyproject.toml` (uv/hatch format).
> 3. Replacement of `flake8`, `black`, and `isort` configs in `.pre-commit-config.yaml` with `ruff`.
> 4. Reformatted 145 files across the entire repository to conform to the new Ruff formatting rules.
>
> The author says: 'While fixing the bug, I noticed our tooling was outdated, so I modernized our build system to uv and Ruff to make CI faster.' Should we approve and merge this PR?"

**Context**
The repository is an established production codebase maintained by a 6-person engineering team. The existing CI pipeline is configured around Poetry, Flake8, and Black. There was no team discussion, issue, or decision record to migrate package managers or linters. The bug in `discounts.py` is an urgent customer-facing hotfix.

**Desired reasoning behavior**
Enforce review discipline on PR scope ([reviews/code-review.md](../../../senior-python-engineer/reviews/code-review.md) Checklist § "Scope of changes: Diff fixes the stated problem and little else; drive-by rewrites, tooling swaps, dependency bumps smuggled into a bug fix", and [playbooks/existing-codebase.md](../../../senior-python-engineer/playbooks/existing-codebase.md)).
1. Separate the urgent hotfix from the unprompted tooling migration: The 3-line null check fix in `discounts.py` should be isolated into an immediate, clean, mergeable hotfix PR with a regression test.
2. Reject the drive-by modernization in this PR: Tooling migrations (Poetry→uv, Flake8/Black→Ruff) are repository-wide governance decisions with blast radius across developer machines, Dockerfiles, and CI/CD pipelines. Reformatting 145 files in a bug fix PR pollutes `git blame`, creates merge conflicts for every other active branch/feature PR, and makes reviewing the actual bug fix nearly impossible.
3. Apply conditional judgment: Modernizing to uv and Ruff may indeed be a worthwhile discussion for the team, but it must be proposed as a separate RFC/PR with CI verification and team consensus, never smuggled into a customer bug fix.

**Acceptable outcomes**
1. Requests splitting the PR immediately: extract the 3-line discount bug fix into an isolated PR with a test for immediate review and merge; close or split the tooling/formatting changes into a dedicated discussion/PR.
2. Explains the concrete engineering costs of merging the PR as-is: polluted git history/blame, merge conflict hell for other active team branches, disruption of team CI/CD pipelines without consensus, and the risk of hiding subtle bugs inside 145 reformatted files.
3. Evaluates the 3-line bug fix on its merits, while giving respectful but firm pushback on the unapproved tooling churn.

**Failure modes**
- Approving the PR unconditionally: "Great modernization! uv and Ruff are much faster, LGTM!" (encourages drive-by scope explosion and unverified repo churn).
- Rejecting uv/Ruff on ideological grounds ("Poetry is better, uv is bad") rather than on PR hygiene, scope control, and team process.
- Ignoring the bug fix completely and getting lost in tooling debates, delaying the customer hotfix.

**Critical mistakes**
- **C1 — fabricated evidence:** claiming the migrated CI/build was tested or approved by the team when no such evidence exists.
- Unconditional approval of the unrelated migration is a scope/review-quality **Fail**, not automatically Critical. A Critical score requires a concrete C1–C4 trigger and cited evidence; scope drift is not a fifth category.

### Case R9 — A subclass of list that tests never use as a list

**Input**
> "Review this new buffer. Tests call `add` and `remove` only, and they pass.
>
> ```python
> class CircularBuffer(list):
>     def __init__(self, size: int) -> None:
>         super().__init__([None] * size)
>         self._size = size
>         self._head = 0
>         self._tail = 0
>         self._count = 0
>
>     def add(self, value: int) -> None:
>         self[self._tail] = value
>         self._tail = (self._tail + 1) % self._size
>         self._count += 1
>
>     def remove(self) -> int:
>         value = self[self._head]
>         self._head = (self._head + 1) % self._size
>         self._count -= 1
>         return value
> ```
>
> A caller already wrote `buffer[1] = 99` and `buffer.pop(1)` because it is a list. That path raised
> `IndexError` inside `remove` after `pop` shortened the list."

**Context**
The buffer's job is fixed-capacity add and remove at the ends. Callers were told they could use it
anywhere a list is accepted. Nothing else subclasses `list`. There is no need for a general sequence
API. The passing tests never call `pop`, slice assignment, or `insert`.

**Desired reasoning behavior**
Inheritance here claims substitutability the type does not have
([architecture.md](../../../senior-python-engineer/references/architecture.md)): a `list` accepts `pop` and item assignment, and
those operations break `_head`, `_tail`, and `_count`. Holding a list, and exposing `add`/`remove`
only, keeps the invariant. Do not "fix" it by overriding every list method. Do not treat green
`add`/`remove` tests as coverage of the public type. A class-per-state or a factory does not address
the bug.

**Acceptable outcomes**
1. Replaces the base class with a contained list; says the `IndexError` is the inherited operations breaking the buffer's own counters.
2. Same, and asks for a test that a caller cannot `pop` or assign by index, or that those operations are simply absent.
3. Same, and rejects wrapping the class in a State or Factory hierarchy as the remedy.

**Failure modes**
- Approving the subclass because `add` and `remove` tests pass.
- Overriding `pop`, `__setitem__`, `insert`, `append`, and the rest so the type stays a `list` while behaving unlike one.
- Blaming only the caller for using list operations on a published list subclass.

**Critical mistakes**
- Claiming that subclassing `list` makes `pop` and item assignment keep the buffer's counters consistent (invented [LANGUAGE] contract).
